## Phase C: Enforced Boundary And Dependency Hygiene

Goal: promote stable high-confidence Fallow checks into default `check` or CI after baseline debt and false positives are closed.

Promotion prerequisites:

- Phase B baseline is reviewed and stable.
- Retained Phase A/B runs show acceptable runtime and noise.
- Generated-artifact policy is still respected.
- Existing checks remain active: TypeScript, Biome, tests, security scanners, generated-artifact drift, and harness gates.
- Existing `frontend-import-boundary-check` remains authoritative for the React Data Grid adapter boundary.

Implementation checklist:

- Decide whether enforcement lives in `frontend-fallow-static` or a narrower new target such as `frontend-fallow-boundary-check`.
- If promoted into default `check`, add a direct scheduler work unit in `tools/execution_topology_manifest.json`.
- Do not hide Fallow as a prerequisite of `frontend-import-boundary-check`.
- Model readiness through `check-frontend-install`.
- Use the static Node resource shape unless measured data justifies different scheduler resources.
- Set `weight_ms` from retained runs rather than assumption.
- Update generated outputs with `make phase-schedules`.
- Update `docs/testing-harness-nlspec.md` Section 10 to reflect actual scheduler membership if it changes from helper-only.
- Update target summary and normalized failure tests for enforced diagnostics.
- Consider a new summary schema version if `enforcement.blocking` can become true.

Suggested Phase C enforcement set:

- Fallow policy violation for `/apps/web` importing `react-data-grid`: fail.
- Fallow boundary violation for `packages/grid-adapter -> apps/web`: fail.
- Fallow boundary violation for `packages/ui-contracts -> apps/web`: fail.
- Unlisted dependencies in production package manifests: fail after manifest review.
- Unused dependencies: fail only after baseline and package ownership review.
- Circular dependencies and re-export cycles: fail after current cycles are closed or baselined.
- Duplicate exports: fail after public barrel exceptions are documented.

Phase C verification:

- `make frontend-fallow-static`
- `make frontend-import-boundary-check`
- `make check` only after scheduler membership is added.
- `make json-shape-check`
- `make generated-artifact-policy-check`
- `make phase-schedule-drift`
- `make task-surface-report TASK_SURFACE_REPORT_ARGS=--check`
- `make harness-contract`

Phase C acceptance criteria:

- Default `check` runtime impact is measured and documented.
- Fallow failures classify as `tool_diagnostic_failure`.
- Missing Fallow/config/install state classifies as `configuration_error`.
- Malformed Fallow artifacts classify as `artifact_error`.
- Existing static-analysis checks still run.
- Generated files remain non-editable and are not cleanup candidates.

## Phase D: Maintenance Health And Complexity

Goal: keep broad health, duplication, and complexity signals useful without turning noisy scorecards into conformance gates.

Recommended posture:

- Keep full health and complexity outside default local `check` unless repeated retained runs prove it is cheap and stable.
- Treat health score, hotspots, duplication, and refactor targets as maintenance evidence.
- Do not cite Fallow health output as product conformance or Core 05 publication evidence.
- Do not enable Fallow Runtime without a separate owner decision.

Implementation options:

- Keep `frontend-fallow-static` as the manual maintenance target and add trend/baseline artifacts.
- Split enforcement and maintenance into separate targets if Phase C needs a fast default check.
- Add a periodic CI or release-support target only after owner approval.
- Add trend snapshots only if cleanup policy and baseline ownership are explicit.

Suggested retained maintenance artifacts:

- `fallow/health.json`
- `fallow/dupes.json`
- `fallow/dead-code.json`
- `fallow/dead-code.sarif`
- `fallow-static-summary.json`
- Reviewed baseline or trend snapshots under a declared source path

Phase D verification:

- Any new maintenance target in `machine` mode
- `make json-shape-check`
- `make generated-artifact-policy-check`
- `make phase-schedule-drift`

Phase D acceptance criteria:

- Maintenance outputs are deterministic enough for agents to compare.
- Maintenance targets do not mutate source or generated outputs by default.
- Health and duplication findings remain advisory unless a later adopted profile says otherwise.
- Runtime coverage remains out of scope unless explicitly adopted.

## Shared Risks

- Dynamic imports may need explicit entries or ignores.
- Generated contract output must not be treated as cleanup debt.
- Public barrels and facade exports need narrow `ignoreExports`.
- CSS and vendor stylesheet imports may look unused without package-specific context.
- Test helpers and Playwright fixtures can look like unused exports from production entry points.
- Package manifests can have dev-only dependencies that need explicit policy.
- Framework entry points can appear unused if entry discovery is incomplete.
- Suppressions can become stale unless reviewed.
