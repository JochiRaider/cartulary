# incidents Module Refactoring Tracker and Handoff

## 1. Scope and Source Posture

Target directory: `internal/modules/incidents`.

Output path: `docs/handoffs/incidents-module-refactor-tracker.md`.

This tracker was created as a planning and documentation artifact. It does not itself authorize production refactors, generated-code changes, migrations, contract changes, route changes, behavior changes, or test rewrites. A follow-up implementation task on 2026-07-02 authorized the remediation slices now recorded in the handoff log.

Allowed planning changes:

- Inventory current files, public surfaces, callers, contracts, tests, and harness mappings.
- Record boundary and coupling findings as planning evidence.
- Propose behavior-preserving workstreams and refactor slices.
- Mark unresolved facts as `TODO:`.
- Mark owner-document contradictions as `BLOCKED: owner contradiction`.
- Mark repository/framework mismatches as planning findings and adapt to the repository.

Non-goals:

- Do not assume `internal/modules/incidents` is a valid permanent module boundary merely because the directory exists.
- Do not move workbook, saved-view, projection, revision, import, evidence, entity, collaboration, link, or view-contract logic in this tracker.
- Do not hand-edit generated roots declared by `tools/generated_artifact_policy.json`.
- Do not treat phase maps, task rows, or tests as runtime architecture.

Source hierarchy for this tracker:

1. Adopted subsystem NLSpecs for their named subsystem only.
2. Core 00 through Core 04 for implementation-conformance behavior.
3. Core 05 only for claim-bearing timed or fixture-sensitive publication.
4. `docs/domain.md` and implementation-support guides for vocabulary, package boundaries, harness mechanics, and execution support.
5. Current repository code and tests for current implementation state.
6. Prior plans and framework files, including `docs/handoffs/cartulary_modular_refactor_planning_framework.md`, as planning evidence rather than authority.

Behavior freeze default: preserve observable behavior unless a later implementation task explicitly authorizes a behavior change. Observable behavior includes route shape, request/response envelopes, WebSocket paths and event semantics, workbook startup and preference behavior, saved-view visibility, storage semantics, authorization outcomes, generated contract surfaces, and harness accounting.

Architectural posture: `internal/modules/incidents` is currently a mixture. It owns legitimate incident lifecycle, membership, and visible-incident behavior, but it also contains transport-adjacent HTTP handling, workbook startup/preferences, saved-view visibility lookup, view-schema pointer validation, extension discovery, WebSocket access revocation side effects, direct SQL/idempotency/audit substrate, and peer-module lifecycle/authz coupling. This is an architectural finding, not an implementation decision.

Implementation status update, 2026-07-02: incident close WebSocket terminal signaling is implemented and characterized; route-level peer consumers now use an incidents access facade instead of concrete `*incidents.Store`; `/api/v1/extensions` is owned by `internal/modules/extensions`; workbook startup/preference public paths are mounted by `internal/modules/workbook` and backed by `internal/modules/workbook/startup`; startup saved-view visibility now goes through a savedviews-owned transactional visibility API. WS-1 removed legacy incidents workbook startup/preference exports, deleted `internal/modules/incidents/startup.go`, moved phase8 startup tests to workbook, and isolated incident-create workbook preference bootstrapping under `internal/modules/workbook/startup/bootstrap`. WS-2 added lifecycle guard and stable error-classification methods to the access facade, migrated peer mutation stores off the exported `EnsureIncidentOpenTx` symbol, and made the transaction guard package-private. WS-3 moved stable incidents and workbook/startup storage operations onto SQLC-generated queries, including incident lifecycle/membership mutations, audit/admin helper queries, workbook preference get/upsert/clear operations, and incident-create workbook preference bootstrap inserts. WS-4 removed production-exported store hook symbols and moved rollback fault injection behind test-runtime guarded `ModuleOverrides` supplied by phase2 testutil. WS-5 centralized route-level incident membership/role outcomes behind incidents access helpers and moved generic session-slide persistence into `httpauth`. WS-6 completed service-backed, browser, finalizer, fast, and full `make check` validation; no authorized remediation workstreams remain open.

## 3. Workbook Boundary Diagnosis

Diagnosis: `internal/modules/incidents` is a mixture of a legitimate incident lifecycle/membership facade, a transport-adjacent adapter, a workbook startup/preference orchestration layer, and a shared authz/lifecycle dependency for peer modules.

It is not safe to declare `incidents` the permanent owner of workbook orchestration just because workbook startup and preferences currently live in this directory. The live repository shows that workbook startup uses view-schema IDs, `sheet_ref` parsing, saved-view visibility, base-surface fallback, and preference pointer clearing. Those are workbook/view-contract/savedviews concerns that currently happen to be implemented through incident routes and store methods.
