# Testing Harness Recovery Partial Completion State List

## Document Role

This S5 artifact records caller-visible states where a harness entrypoint can
complete some setup, child work, reporting, or cleanup but not reach normal
success or verified cleanup. These states are inputs to S6 hazard/timing work
and S8 authority decisions.

## Classification Rules

- A partial-completion state must identify the output left behind and the
  cleanup/resource follow-up that is known, unknown, or authority-bound.
- `observed` means S5 read source that creates the state; `runtime_observed`
  would require selected retained artifacts or a safe non-mutating command
  observation; `source_limit` remains when runtime behavior was not exercised.
- Product assertion partials are separated from harness operational partials
  when setup succeeded and the child test itself failed.

## Checklist Support

| Field | Value |
|---|---|
| Status | `complete` |
| Blockers | Runtime partials for Docker, service-backed work, browser stacks, reset calls, cleanup, parent death, and provider CI annotations remain unobserved. |
| Findings | `PCS-0001` through `PCS-0019` identify observable partial states, retained outputs, cleanup expectations, retryability, and ownership. |
| Source limits | Runtime cleanup/reaper completion, active connection cleanup, port release, failure-only bundles, stale artifact provenance, and direct package cleanup remain source-limited. |
| Ambiguities | Reset-route authority, package-script contract status, local-dev persistence, platform profile, janitor bounds, and external cache cleanup route to S8. |
| Handoff notes | S6 can use these rows as candidate probes for cleanup, timing, race, capacity, timeout, interrupt, and parent-death analysis. |
| Evidence status | Rows use `observed`, `observed/source_limit`, or `source_limit`. |
| No-change confirmation | This file records recovery documentation only and does not alter harness behavior. |
