### 4.2 Exact-match key contract

| Key kind | Accepted source field | Authoritative stored value | Equality and claim value | Case posture | Precedence |
| --- | --- | --- | --- | --- | --- |
| `primary_email` | `party.primary_email` | `email_address_v1` normalized value; letter case MAY be preserved. | Locale-independent case-insensitive form produced from the normalized value. | Case-insensitive. | First. |
| `external_ref` | `party.external_ref` | `locator_text_v1` normalized value. | Exact Unicode code-point sequence of the stored normalized value. | Case-sensitive; query filtering does not redefine identity. | Second. |

For create, explicit create-from-text, patch, restore, rollback, Imports, Incident Bundle import, and recovery, the later adopted algorithm MUST execute in this order:

1. Complete field admission for every supplied field.
2. Return an exact committed replay before reading current Party or claim state.
3. Reject a divergent replay as `client_txn_conflict` before current-state evaluation.
4. Normalize every supplied non-null exact-match field.
5. Restrict claim resolution to active Parties in the same incident.
6. Resolve all supplied keys before applying precedence.
7. If one key resolves to multiple active Parties, fail with `ambiguous_exact_match`.
8. If supplied keys resolve to different Parties, fail with `cross_key_exact_match`.
9. If all non-empty matches converge on one Party, reuse that Party. Precedence selects only the internal `matched_by` value.
10. If no key matches, acquire all proposed claims and then create the Party.
11. A uniqueness race or an existing Party acquiring another Party's key fails with `exact_match_key_claimed`.
12. On any failure, commit no Party, Records envelope change, claim, revision, projection refresh, collaboration event, idempotent success, or Imports outcome.

The internal result MAY carry `matched_by=primary_email`, `matched_by=external_ref`, or `matched_by=null`. It MUST NOT add a new public Workbook or Imports member without a separately adopted public contract. Reuse retains the current `reuse` revision posture and MUST NOT overwrite or enrich the existing Party.

### 4.3 Party-owned active-claim contract

The logical identity is exactly:

`(incident_id, party_key_kind, normalized_value) -> party_record_id`

| Rule | Required behavior |
| --- | --- |
| Key vocabulary | `party_key_kind` is exactly `primary_email` or `external_ref`. |
| Presence | A claim exists if and only if the Party is active and its corresponding field is non-null. |
| Uniqueness | One claim tuple maps to exactly one Party. Multiple canonical copies on one Party remain one logical claim. |
| Locking | Old, current, and proposed tuples are locked in bytewise ascending order over the complete tuple. |
| Clear | Clearing a field releases its claim in the same transaction. |
| Delete | Soft deletion releases both claims in the same transaction. |
| Restore and rollback | The operation reacquires the exact resulting claim set or fails atomically with `exact_match_key_claimed`. |
| Imports and Incident Bundles | Both consume the same Party semantics; neither owns or reinterprets claims. |
| Recovery | Claim bytes are not restored. Recovery rebuilds deterministically from authoritative Records and Party rows, validates exact set equality, and blocks readiness on duplicates or drift. |
| Publication | Claims are not records, workbook rows, links, public resources, Party portable rows, or authoritative backup members. |
| Migration | Preflight reports conflicting record IDs, field keys, and safe reasons to operators, blocks the migration, and never selects, merges, deletes, or edits a winner. |
