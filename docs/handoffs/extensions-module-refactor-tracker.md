## 3. Module Boundary Diagnosis

The live package is a legitimate thin-to-medium Extensions coordination facade
combined with transport-adjacent, persistence-adjacent, and generic mutation
coordination. It is therefore a **mixed-responsibility package**. It is not an
accidental domain catch-all: repository inspection found no timeline,
projection-refresh, entities/indicators, evidence, links, saved-view, view-schema,
collaboration-handler, frontend-controller, or grid-vendor implementation inside
the target.

Frontend availability computation and WebSocket invalidation are adjacent
consumers of Extensions contracts, not implementations owned by this package. The
package is not itself a frontend shell/controller surface or grid-vendor
integration layer.

### Resolved physical package map and dependency direction

RB-002 is resolved at the design level. The map below is an
implementation-support decision, not a new normative owner assignment:

| Current content | Selected target | Content moved later | Extensions content retained |
| --- | --- | --- | --- |
| `transaction.go` execution protocol | New `internal/modules/crossownertransaction` | Participant ordering, prepare/validate/write sequencing, aggregate limits, serialization ordering, final transaction, rollback, cancellation, and commit-outcome classification | Generated participant catalog, descriptor/binding admission, canonical participant identity, and declaration/binding parity |
| Portability orchestration in `portability.go` | Existing `internal/modules/incidentbundles` | Import/export operation orchestration, participant order, preparation, aggregation, and public portability error mapping | Portability mode and blocking declarations, participant catalog lookup, and result-schema admission |
| `StagedOutputScope` and staged cleanup | New `internal/modules/stagedobjects` | Allocation, abandon/transfer, publication ownership, cleanup, retry, and readiness integration | Profile/contribution identity used to authorize an allocation |
| `backup.go` orchestration | Existing `internal/modules/recovery` | Restore admission, codec selection, group/binding sequencing, validation invocation, failed-target state, and `MayServe` | Generated backup binding/codec catalogs, profile provenance, and binding parity |
| `deadline.go` pure policy | New `internal/modules/extensions/deadline` | Entire pure `extension_deadline_v1` arithmetic and outcome precedence helper | The dedicated package remains Extensions-owned; Core 04 still owns configuration, process lifecycle, and fatal consequences |
| `inactive_configuration.go` invocation | Existing `internal/platform/config`; use `internal/platform/config/extensioninactive` only if a focused subpackage is needed | Syntax-only invocation, value discard, and startup finding conversion | Generated profile configuration-contract data and immutable inactive-policy declarations |

Implementation must preserve these dependency rules:

- `internal/app/server` composes Extensions, cross-owner transactions, Incident
  Portability, staged objects, recovery, and platform configuration.
- Each semantic owner defines the narrow port it consumes; app composition
  translates immutable Extensions catalog views to owner-local values.
- Shared owner packages do not import the broad
  `internal/modules/extensions` facade merely to obtain a helper. They may
  consume a narrow immutable catalog port or the focused
  `internal/modules/extensions/deadline` package.
- Profile packages implement typed participant or validator ports and are
  injected by application composition. Shared coordinators do not import profile
  packages.
- Platform DTOs, SQL rows, `pgx` transactions, storage sessions, and object keys
  remain behind platform adapters.
- No reflection, runtime plugin scan, generic callback bus, dynamic registration,
  or broad `ExtensionsServices` interface is introduced.
- Internal moves use no compatibility shim. Tests and Harness ownership move
  with the responsibility, and test-only helpers are not wired into production
  merely because their destination is selected.

Before creating either new package, implementation must re-run an exact live-tree
search and merge with any owner package added since this baseline. There may be
only one recovery, staged-object, transaction, or configuration owner.

### Publication serving-epoch consumer map

RB-004 is resolved at the design level: `PublicationPlan` is the immutable,
process-local admission and activation epoch. It is not an audit artifact,
persisted object, log payload, or behavior owner. Exact production consumption
remains blocked on app-server characterization.

| Consumer | Required typed epoch projection | Live evidence and remaining gap |
| --- | --- | --- |
| HTTP extension dispatcher | Route dispatch plan containing every recognized reserved family and its `claimed` or `inactive` state | The live dispatcher receives separately constructed HTTP profiles; no `PublicationPlan.Routes()` production caller was found. |
| Discovery handler | Resolved claims plus registry descriptors from the installed epoch | `runtime.go` separately builds `profiles` from descriptors and resolved claim IDs, then passes them to HTTP dependencies. Parity and epoch identity are not characterized. |
| Workbook startup and client availability | Workspace registry plus the current client-support registry | Frontend availability consumes discovery/support/current-generation state, but no app-server plan identity is propagated or tested. |
| Worker manager | Worker plan plus implementation bindings | No `PublicationPlan.Workers()` production caller was found. Quiescent preparation, binding identity, and gate acknowledgment require characterization. |
| Listener and admission controller | Listener plan plus exact acknowledgment identities | `Runtime.ActivatePublication` publishes the lifecycle gate, but the live plan is not passed to the lifecycle object and exact component acknowledgments are not characterized. |
| Job admission and dequeue | Installed serving gate, claims, worker plan, and job-kind contracts from one epoch | No plan projection consumer was found; independent job wiring must be mapped before change. |
| Telemetry | Canonical resolved claims or digest from the installed epoch | Runtime telemetry receives `ResolvedClaimSet` directly. Same-input derivation exists, but same installed-epoch identity is not proved. |
| Conformance/static diagnostics | Plan and component identities from the same build | Coordinator tests prove component digests; no runtime single-epoch test covers all consumers. |

No consumer may independently re-derive claimed routes, workspaces, workers,
listeners, capabilities, or bindings after the epoch is installed. A future
application-owned `PublicationController` or equivalent is the sole installer.
All consumers must switch in one atomic implementation slice; a mixed legacy and
plan-derived serving path is not an acceptable intermediate production state.

immediately before commit; after PostgreSQL commit before client success is
observed; during committed-transition readback; during rollback; and during
profile-lock acquisition or release. Arbitrary sleeps are not acceptable fault
injection.

read/write operations rather than renamed platform DTOs. One profile session
holds the deployment-global lock across initialization or all independently
committed migration steps and final validation. Commit results remain the closed
semantic set `committed`, `absent`, or `indeterminate`.
