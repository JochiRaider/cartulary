### 4.2 Conflict-token and `keep_saved` freeze

The structural refactor MUST preserve conflict-token version `2`, the exact
encoded bytes for identical inputs, current claim names and meanings, HMAC-SHA256
calculation, constant-time MAC comparison, and the existing dedicated key

authenticates integrity and origin; it does not provide confidentiality.

The current version has no expiry or key identifier. Key rotation is therefore
outside this structural refactor. RS-08 MUST NOT introduce multiple verification
keys, reinterpret existing bytes, or change token lifetime. A future rotation
design requires separate owner and compatibility authorization, a new closed
version when the wire shape changes, an explicit overlap duration, and tests for

For `keep_saved`, admission and consequences are exact:

1. The route MUST perform ordinary authentication, cookie CSRF, hidden-resource,
   and role checks before exposing token or body failures.
2. The adapter MUST verify route, record, view-schema, field, row-window, and
   normalized-request bindings.
3. A non-replayed valid attempt MUST dispatch to the authoritative source owner
   for incident-lifecycle, target, field, and current conflict-window
   revalidation in the caller-owned transaction.
4. A stale conflict window MUST return a fresh `same_field_conflict`; it MUST
   preserve the client draft and MUST store no idempotency success.
5. Idempotency scope is exactly route, authenticated actor, record, and
   `client_txn_id`. Exact successful replay returns the stored result after
   ordinary route authorization without repeating source mutation. Divergent
   reuse returns `client_txn_conflict`. A new key is a new attempt and repeats
   source revalidation.
6. Success and exact replay create no source mutation, `change_set`, mutation
   entry, record revision, projection update, or `record_changed` intent.
