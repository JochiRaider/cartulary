### 4.1 Timeline version-identifier writer contract

The future Core 02 amendment MUST adopt one writer format. Current divergence is implementation state to remove, not a compatibility contract.

| Mutation origin | Required emitted value | Required derivation |
| --- | --- | --- |
| Timeline-owned create, patch, lifecycle, clipboard, bulk, supersede, restore, rollback-result, or other Timeline source mutation | `timeline_record:<record_id>:<row_version>` | `record_id` and `row_version` MUST come from the mutation's authoritative Timeline target and corresponding canonical before or after snapshot. |
| Timeline source-row version advance committed as a subordinate effect of an Entity mention lifecycle action | `timeline_record:<record_id>:<row_version>` | `record_id` and `row_version` MUST come from the same authoritative Timeline target and snapshot represented by the subordinate mutation. |

The planned implementation interface is `versionid.Format(recordID uuid.UUID, rowVersion int64) string` in `internal/modules/timeline/versionid`. All Timeline-owned writers MUST call it. The caller MUST supply the authoritative non-zero record UUID and a positive row version; no zero, omitted, or malformed input has a formatter default.

- `<record_id>` MUST be the lowercase, hyphenated canonical UUID of the mutation's Timeline target and MUST equal mutation `target_id`.
- `<row_version>` MUST be the canonical positive decimal representation of the corresponding snapshot row version, with no sign and no leading zero.
- `timeline_record` MUST remain the Revisions `target_kind`; `timeline_event` MUST remain the source `record_type`.
- `timeline:` MUST NOT be emitted, synthesized, accepted as a writer default, or retained in a Timeline-owned fixture after TL-S05.
- A new writer grammar requires a later owner amendment; package movement MUST NOT create a second formatter.

### 4.2 Opaque readers and pre-production cutover contract

Generic consumers MUST continue treating the complete identifier as opaque. Opacity is an architectural boundary, not a promise to support pre-cutover Timeline data.

- Revisions MUST NOT derive target kind, target identity, record type, authorization, rollback provider, source owner, relation, SQL identifier, or dispatch behavior from the prefix.
- Recovery and rollback MUST use target semantics, canonical snapshots, and authoritative row versions; they MUST NOT parse a Timeline prefix.
- Current canonical Incident Bundle export, validation staging, import, persistence, and re-export MUST preserve every non-null value byte-for-byte.
- Existing history or conflict surfaces that carry the current value MUST pass it through exactly. This plan MUST NOT add the value to a new public surface.
- No read-time default exists. An omitted or JSON `null` value retains its operation-specific meaning; a reader MUST NOT synthesize a prefix.
- Generic schema admission MAY incidentally carry an unfamiliar opaque string, but pre-cutover databases and bundles are unsupported and receive no acceptance criterion.

The cutover MUST use repository reset mechanics instead of compatibility code. An operator MAY preview the destructive database action with `CARTULARY_CLEANUP_DRY_RUN=1 make db-reset`. A real pre-production reset requires separate operator authorization and `CARTULARY_DESTRUCTIVE_CONFIRM=db-reset make db-reset`; implementation agents MUST NOT perform it implicitly.
