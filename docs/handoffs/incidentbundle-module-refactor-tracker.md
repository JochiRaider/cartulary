# incidentbundles Module Refactoring Tracker and Handoff

## 1. Scope and Source Posture

Target directory: `internal/modules/incidentbundles`.

This tracker began as a planning-only handoff artifact. A later implementation task authorized the first remediation pass: import-finalization characterization, owner finalization wiring, projection rebuild port wiring, and frontend terminal-code fixture alignment. It still authorizes no generated output change, migration rewrite, public contract change, bundle-format change, or broad source-family port extraction without an explicit follow-up implementation slice.

Non-goals unless separately authorized: generated roots, migrations, contract artifacts, phase maps, scheduler manifests, lock/tool-managed files, and bundle v1 wire-format changes.

Authority order used for this tracker:

1. Adopted subsystem NLSpecs for their named subsystem only.
2. Core 00 through Core 04 for implementation-conformance behavior.
3. Core 05 only for claim-bearing timed or fixture-sensitive publication.
4. `docs/domain.md` and implementation-support guides for terminology, package boundaries, harness mechanics, and execution support.
5. Current repository code and tests for implementation state.
6. Prior plans and framework files as evidence, not authority.

No owner-document contradiction was found during inspection. Repo/framework mismatch recorded: the modular refactor framework catalog does not list `incidentbundles`, while Core 01 explicitly allows `incidentbundles` as a repository-level refinement for Incident Portability export/import state. This mismatch is a planning finding, not proof that `incidentbundles` is a clean permanent module boundary.

Architectural finding: `internal/modules/incidentbundles` is a real Incident Portability extension facade today, but it is a mixture, not a clean permanent module boundary. It owns route admission, descriptor/job state, bundle archive format, and portability-specific tables. It also directly exports/imports source tables owned by timeline, entities, indicators, evidence, links, revisions, savedviews, incidents, projections, and assessments through raw SQL. Those responsibilities should move behind owner-provided ports before any code movement.

## 3. Workbook Boundary Diagnosis

Diagnosis: the current package is a mixture. It is a legitimate thin facade only for the public Incident Portability route family, export descriptor/job state, and archive-format verification. It is also an accidental catch-all for cross-module source serialization, import mutation, projection rebuild, evidence blob byte movement, incident bootstrap membership, imported attribution, and history/revision preservation.

The package is not primarily workbook orchestration. It affects workbook behavior indirectly by importing source state, rebuilding projections, preserving saved views, preserving revision/change-set state, and enabling imported incident startup. Those behaviors must preserve observable workbook outcomes while moving ownership behind clearer module boundaries.
